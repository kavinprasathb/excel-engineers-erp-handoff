# Handoff: Excel Engineers ERP (v3)

Read this first. It is written for an engineer or AI agent picking the project up on a
new machine. `README.md` has the short setup notes, and `docs/` has the deeper material.

## 1. What this is

An order-management ERP for **Excel Engineers, Salem**, an authorised **KSB pump dealer**.
It covers quotations (with revisions and negotiation), orders, purchase orders, inventory,
customers and suppliers, staff and reports. PDFs (quotation letters, POs, challans and
reports) are generated on the server in the company's letterhead style.

The app is live in production, so real business data depends on it. Deployment access is
**not** part of this repo (see section 8).

## 2. Stack

| Layer | Tech |
|---|---|
| Backend | Python 3.12 (`uv`), FastAPI, SQLAlchemy 2, Alembic, Pydantic v2, ReportLab |
| Frontend | React 19, Vite, TypeScript, Tailwind v4, TanStack Query, Vitest + MSW |
| Database | Postgres 16 with the `pg_trgm` extension |
| Production | Docker Compose on a VPS, with nginx and HTTPS in front |


## 4. Local setup (any OS)

You need Python 3.12 + [`uv`](https://docs.astral.sh/uv/), Node 22, and Postgres 16.
Docker is fine for the database if you don't want a native install:

```bash
docker run -d --name excel-pg -p 5432:5432 -e POSTGRES_USER=excel -e POSTGRES_PASSWORD=excel postgres:16
```

Then:

```bash
# databases (the pg_trgm extension is required)
psql -h localhost -U excel -c "CREATE DATABASE excel"      # skip if the container already made it
psql -h localhost -U excel -c "CREATE DATABASE excel_test"
psql -h localhost -U excel -d excel      -c "CREATE EXTENSION IF NOT EXISTS pg_trgm"
psql -h localhost -U excel -d excel_test -c "CREATE EXTENSION IF NOT EXISTS pg_trgm"

cp backend/.env.example backend/.env     # defaults work locally; ENVIRONMENT=development

cd backend  && uv sync && uv run alembic upgrade head
cd frontend && npm install

# two terminals
cd backend  && uv run uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
cd frontend && npm run dev
```

Open **http://localhost:5173**. Use `localhost`, not `127.0.0.1`, or the login cookie
won't stick. Log in with `ADMIN_EMAIL` / `ADMIN_PASSWORD` from `backend/.env`; that
admin is created on startup.
Health check: http://localhost:5173/api/health should show `"db":"ok"`.

Optional sample data: `cd backend && uv run python -m scripts.seed_sample_data`.

The local database starts empty. Live data is **not** in the repo. If you need a copy,
ask the project owner for a sanitised dump.

## 5. Checks (run all before handing work back)

```bash
cd backend  && uv run pytest -n 6 && uv run ruff check . && uv run mypy app
cd frontend && npm run test -- --run && npm run lint && npx tsc -b
```

- On Node 23+, prefix the frontend tests with `NODE_OPTIONS=--no-experimental-webstorage`.
  The newer built-in `localStorage` breaks some tests.
- The backend tests can rewrite two files in `backend/tests/fixtures/`. Undo that with
  `git restore backend/tests/fixtures/` before committing.

## 6. Rules (non-negotiable; the owner insists on these)

1. **Never lose or break existing data.** Every Alembic migration must keep data intact
   and must have a working `downgrade()`. `test_migrations` runs upgrade → downgrade →
   upgrade. Read every autogenerated migration before keeping it.
2. **Don't touch unrelated features.** Change only what the task asks for. Other
   workflows (quotation → negotiation → revision → order → PO) must keep working.
3. **Money is integer paise** (`BigInteger`), and it is formatted only in the browser.
4. **GST is basis points**: `1800` = 18%.
5. **All stock changes go through `backend/app/services/stock.py`.** A session guard
   raises on anything else.
6. `quantity_available` is a Postgres generated column. Never compute it in code.
7. Secrets live only in `.env` files, which git ignores. Never commit one.
8. Match the surrounding code style. New behaviour needs tests: pytest in
   `backend/tests`, Vitest next to the component.

## 7. Domain notes (what's been built recently)

- **Quotations** have types *pumps*, *valves* and *spares*, and three offer layouts:
  - **Pump**: a priced table.
  - **Spares**: part numbers and MOC.
  - **Technical**: a datasheet with pumps side by side, 6 per table; rows that are
    the same for every pump are merged.

  Code: `modern_pdf.py`, `frontend/src/features/quotations/components/OfferLayoutPicker.tsx`
  and `TechSheetEditor.tsx`.
- **Revisions**: each revision is its own row, numbered like the client's scheme
  (`ESQP-25-062R2`). Negotiation history is tracked.
- **Multi-item lines**: the line rate is the sum of its items.
- **Margin %** is calculated on cost and can go above 100%.
- **Items not in inventory**: a product's `stock_type` is *stocked*, *to order* or
  *service*.
  - Service lines skip stock reservation and delivery.
  - Quick-add is in the product picker.
  - SKUs are `ITM-`, `ORD-` and `SRV-` (`services/products.py`).
- **Earlier-quote suggestions**: typing a line description shows matching past items,
  with customer, date, rate and HSN; picking one fills the line.
  - Code: `services/item_suggestions.py`, `GET /api/quotations/item-suggestions` and
    `DescriptionSuggestions.tsx`.
  - Data source: the `past_offer_items` table, filled by `scripts/import_past_offers.py`.
- **Branding**: the logo is a vector rebuild of "Excel Engineers – Total solutions in
  fluid mechanics". Files are in `frontend/public/brand/` and `backend/app/assets/`.
- **Import scripts** (`backend/scripts/`) read the owner's local Word/Excel files. They
  are already applied to live, and you don't need to run them again.

## 8. Deployment: not for you

Deployment is done **only by the project owner**. This repo deliberately contains no
server address, passwords or keys; they appear as `<VPS_IP>` / `<LIVE_DOMAIN>`
placeholders in `docs/runbook.md` and `deploy/`.

- Don't try to deploy, SSH, or connect to the production database.
- In `Makefile`, `make tunnel` / `scripts/db-tunnel.sh` would connect to the live
  database. **Don't use them.** Always develop against your own local Postgres.
- When your work is ready, push a branch and open a pull request. In the PR, describe
  any migration and confirm the checks in section 5 pass. The owner reviews it and
  deploys it.
